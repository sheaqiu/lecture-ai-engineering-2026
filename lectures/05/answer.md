- 気づき・疑問：

## 宿題

- 取り組んだレベル：発展
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  - `app/agent.py` を拡張し、質問の性質に応じて **RAG（`search_materials`）・Tree（`browse_tree`）・Graph（`search_graph`）の3ツールを自動で使い分ける `--auto` モード**（Agentic Routing）を実装した。
  - 具体的には、`AUTO_INSTRUCTIONS`（単点定義はRAG、全体構成・章立てはTree、複数ページにまたがる関連はGraphを優先し、不足時は別ツールで補完する指針）を追加し、`--auto` 指定時に3ツールすべてを `Agent` に渡すようにした。既存モードや `uv run pytest -q`（21 passed）を壊さない形で追加している。
- 比較した質問と、固定した条件（モデル・対象資料など）：
  - **固定条件**：モデル `gemini-3.5-flash-lite`、対象資料は第1〜3回本講義（214ページ）、比較対象はベースラインの通常RAG（デフォルト）と新設の `--auto`。
  - **Q1（単点事実）**：`第2回で説明されているLoRAでは何を固定して何を学習しますか？また、QLoRAではそれに何が加わりますか？`
  - **Q2（複数ページ関連）**：`第3回で説明されているcompactionと、セッションをまたぐ記憶（長期記憶）はそれぞれどのような役割で、どう関係していますか？`
  - **Q3（全体構成・目次）**：`第2回「基盤モデルの仕組み」の講義全体は、どのような章立て（構成）になっていますか？`
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

|---|---|---|---|---|---|---|---|

- 改善した例と、残る失敗・制約：
  - **改善した例（成功ケース）**：
    1. **Q3（講義構成）で大幅改善**：通常RAGでは全体像を掴むために検索を4回繰り返し（10.96秒・16,072 tokens・$0.004697）かつ「補足」章を取りこぼしたのに対し、`--auto` は自動で `browse_tree` を選択し、わずか2回の目次参照で全章構成を網羅しつつ、**時間約半分（5.74秒）・入力トークン約83%削減（2,730 tokens）・費用約71%削減（$0.001339）**を達成した。
    2. **Q2（跨頁関連）での根拠補完**：`--auto` が自動で `search_graph` を選び、通常RAGで漏れた前後ページ（p.40）も参照して両者の連携・循環関係を具体的に説明できた。
  - **残る失敗・制約**：
    1. **ルーティングの固定オーバーヘッド**：Q1のように通常RAGで十分な質問でも、3ツール分のスキーマと指示文を毎回渡すため、入力トークンが約500 tokens（$0.000349）余分に増える。
    2. **Graph選択時のトークン増加**：Q2では `search_graph` により入力トークンが2倍以上（2,491 → 5,843）に増えており、簡単な比較では過剰な展開になりうる。
    3. **モデル判断への依存**：ルーティングの精度がプロンプトとLLMの判断に依存するため、曖昧な質問ではTreeを誤選択して高レイテンシ化するリスクが残る。
- 気づき・疑問：
  - 単一の検索方式を極めるだけでなく、「質問タイプに応じて取得方式そのものを切り替える」設計にすると、特に構造系の質問（Q3）で精度とコストの両面が大きく改善することを実測で確認できた。実運用では、ツール定義のトークン増を抑えるために軽量な前段ルーターと組み合わせる構成も有効だと感じた。
